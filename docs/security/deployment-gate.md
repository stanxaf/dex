# Deployment gate
AGT-12 in [agent operations](agent-operations.md) keeps production credentials and protected writes out of a non-interactive run. An automated deployment is the single recognised exception, and it is available only while every requirement here holds; failing any one of them leaves AGT-12's prohibition in force and the deployment prohibited. These are conditions on whether the deployment is permitted at all, not explanatory notes, and a deployment taken without meeting them is unapproved however the work was described.

Read this before configuring, requesting or running an automated deployment. Ordinary work does not reach it. The foundation owner approved this pattern and no particular deployment — see [ADR 0002](../decisions/0002-gated-automated-deployment.md).

**Release identity** is what everything below binds to. A release is the complete deployable unit, identified immutably by three things together: the artifact's own content digest; the deployment configuration applied with it — manifests, values, environment and secret references, the migration set, and any flag state the release depends on — pinned by digest or immutable revision; and the target environment's stable identifier. Change any one and it is a different release needing its own approval, because the same artifact with different configuration is a different deployment, and an approval that pins the artifact while leaving configuration floating has approved nothing that can be checked.

- **AGT-15** Each deployment runs under an approval bound to a complete release identity. A tag, branch, build number, `latest`, version string, mutable config branch or "current" environment alias can be repointed or rebuilt after approval, so an approval resting on one of those names no release. A standing approval, an approval given for an earlier release, an approval that names the artifact but leaves its configuration unpinned, and an approval for one environment used to reach another are all absent approvals for the deployment at hand.
- **AGT-16** The gate verifies the deployment it is about to perform instead of trusting the request that reached it. Before releasing credentials it resolves the artifact, the deployment configuration and the target it would actually act on, compares all three against the approved release, and refuses on any mismatch or on a component it cannot resolve. A matching artifact with an unverified or changed configuration is a mismatch, not a detail. Refusal is the correct outcome, not an obstacle: an agent must not retry around it, re-request approval for what failed, or substitute a rebuild. Report a mismatch as a finding under AGT-3, and treat one indicating a repointed or replaced release as an incident under AGT-14.
- **AGT-17** The deployment then acts on the exact release that was verified, by identity rather than by reference: the artifact digest, the configuration revision and the target identifier, all three passed to the deploying step and used as given. Re-resolving a tag, a configuration branch or an environment alias after verification reopens the window AGT-16 closed, because any of them can move between the check and the apply, and the comparison then proves nothing about what actually ran. A deploying step that can only accept a mutable reference for any component does not meet this requirement, and the gate does not conform until every component can be given by identity.
- **AGT-18** The gate sits outside the agent's reach. An agent may request a deployment and report its outcome, and must not be able to grant the approval, approve its own request, alter or re-use an existing approval, change the configuration a release pins, or reconfigure the pipeline to skip the gate or the verification. A gate the agent can edit, disable or route around is not a gate.
- **AGT-19** Deployment credentials are least-privilege and short-lived: scoped to the target environment and the actions that deployment performs, issued for the run, and expired or revoked when it ends. A long-lived production credential reachable from an agent session is ungated production access under AGT-12 whatever the pipeline does with it.
- **AGT-20** The run produces audit evidence tying what ran to its approval: the named approving human (AGT-11), the approved release and the release actually deployed with all three components of each and the result of comparing them, confirmation that the deployment executed against that release, the scope and lifetime of the credentials used, and the actual outcome. Evidence naming a release without its component identities cannot make that link and does not satisfy AGT-13; the deployment is then treated as unapproved rather than as an evidence gap.
- **AGT-21** A conforming gate satisfies AGT-12 and nothing else. The workflow's approval boundaries and every approval the selected profile requires still apply in full — production deployment and auth-change approval under [web-saas](../../profiles/web-saas/PROFILE.md), and independent human validation of calculations and release approval under [regulated](../../profiles/regulated/PROFILE.md). Automating the deployment does not automate those approvals, and a project may require more than these requirements but not less.

These are written rules and enforce nothing by themselves. The gate, the release comparison, the credential scopes and lifetimes, and the audit log must be configured and verified in the platform; see [Codex compatibility](../agent-governance/codex-compatibility.md) for what is and is not guaranteed there.
