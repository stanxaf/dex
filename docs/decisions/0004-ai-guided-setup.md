# ADR 0004: AI-guided setup as the primary adoption path

Status / owner / date / approving authority: accepted on 2026-11-07. Owner and approving authority: **[OWNER NAME PENDING]** — the foundation owner. Stan is recorded as owner for ADR 0002 and ADR 0003, but that confirmation was scoped to those records, so it is not carried over here by inference; fill this before merge.

Scope and non-goals: adds [AI-guided setup](../agent-governance/setup.md) and the `foundation-setup` skill as the primary adoption path, and changes what the installer prints. Distribution is unchanged — [ADR 0001](0001-distribution.md) still stands, the installer still copies a reviewed local checkout, and every ownership, collision, hash, symlink and update protection is untouched. No governance requirement, approval boundary or profile changed, and no managed file was removed.

Context and constraints: adoption required a human to run a command and then work through a long reconciliation checklist spread across the README and the adoption document. That produced two failure modes. Routine entries that the repository plainly evidences — the test command, the lint command, the detected stack — were left blank because the checklist did not distinguish them from entries needing a decision. And the genuinely consequential entries, the owner and the agent's permissions, were sometimes filled with plausible-looking guesses, which is worse than a blank because a blank is visible in review. The installer compounded it by printing success on the last line, which reads as "done" when it means "files copied".

Options considered: (1) shorten the checklist — rejected, because the problem is not length but that it asks a human to do work an agent can evidence, while burying the four questions only the human can answer; (2) have the installer prompt interactively and write the answers — rejected: it would put an installer in the business of recording approvals and ownership, it cannot read a repository for evidence, and a non-interactive run would then either block or silently default; (3) have the installer infer and fill the configuration itself — rejected for the same reason plus a worse one, that inference belongs where it can be reviewed in a diff, not inside a tool whose output nobody reads; (4) make the agent the operator, with the installer reduced to the mechanical copy it already is and a written procedure the agent follows — adopted.

Review corrected five things in the first draft of this work, each recorded here because each was a way the flow could report success it had not earned. A mention of `.ai-governance.md` in an instruction file was treated as proof the foundation was active; it is now evidence to review, since the text may forbid the file, quote it, or point at a path that moved — the one case a tool can settle is a file still byte-identical to the template it installed. Contradictions between existing or nested instructions and the foundation are now reconciled *before* activation rather than listed afterwards, because activating into a conflict is what leaves an agent holding two authorities. The completion test counted decisions as met once they had been presented; presenting is not obtaining, so an unanswered entry now keeps the status at "files installed, setup outstanding". A resumed setup demanded a checkout path it did not need, which pushed people toward whatever checkout was nearest; a checkout is now required only to install or update, and required to be reviewed when it is. And the commit guidance named the whole of `.agents/skills/`, which would sweep a project's own skills into a governance commit, and read as an instruction to commit — it now names `.agents/skills/foundation-*/` and leaves committing to the human.

Decision and rationale: a human's entry point is one sentence naming a reviewed checkout and the path `docs/agent-governance/setup.md`. Naming a path rather than a skill is what makes it work before installation, and AGT-22 already permits reading an instruction set read-only before its rules are known, so the bootstrap needs no new permission. After installation the same procedure is reachable as `$foundation-setup`, so a resumed or repeated setup needs no path. The procedure splits the work by what can be evidenced: entries the repository demonstrates are filled with their evidence cited, and the rest is grouped into four handoff items — people, repository enforcement, agent session limits, automation. It states plainly that an owner, approver, permission, credential scope, approval mode, egress rule, data class or branch-protection setting must never be invented, because a repository cannot evidence any of them. It reconciles contradictions before activating, and treats a mention of `.ai-governance.md` as evidence to read rather than proof of connection, so setup neither activates into a conflict nor adds a second link that INS-1 warns against. The installer creates a root instruction file only when no instruction file that applies to the project exists anywhere, because creating one from the template also activates the foundation. "Anywhere" covers three scopes, because an instruction binds wherever it loads from: files inside the project, files above it up to the Git root, and files at the known global locations. Ancestors matter because instruction files load along the path down to the work, so a file at the root of a repository containing this project applies here and is unreachable by walking the project. Globals matter for the same reason and load earliest of all. They are looked for in the effective Codex home — `CODEX_HOME` when set, otherwise `~/.codex` — covering `AGENTS.override.md`, `AGENTS.md` and `instructions.md`, with override before regular as in a project directory. Only a hardcoded `~/.codex` would miss the file that actually loads for anyone who relocates it. The installer checks existence and reports paths, never contents: these are the user's own files, often private, and reconciling them belongs to the agent and the human rather than to a copier. Where any scope has a file the installer creates nothing, prints `NOT ACTIVATED ON PURPOSE`, and lists each scope separately — naming the ancestor search boundary, or stating that no Git root was found and the boundary could not be established, and stating that the global list is not exhaustive. An earlier revision said global instructions "cannot be inspected from here", which read as licence to ignore them; checking the known paths and admitting the list is partial is the honest version.

Two further corrections came from review. The guidance on framework-managed instruction files said a file a framework rewrites "will discard anything you append", which is false for the common case: a tool that writes a delimited block preserves everything around it. The procedure now requires verifying the behaviour — by reading the writer's upsert logic or running it against a copy — and using the most durable supported location, rather than guessing in either direction. And reconciliation now sorts findings before escalating: a project rule stricter than the foundation is not a conflict and needs no decision, so only genuine contradictions reach the human, which keeps the handoff to the decisions that actually need one. It prints `FILES INSTALLED - SETUP IS NOT COMPLETE`, the active instruction file, what that file mentions, what to reconcile, and what may be committed, so its output feeds the procedure instead of implying completion. A six-condition completion test makes "setup complete" checkable rather than a judgement, and an unanswered decision fails it.

Consequences, migration and recovery: existing adopters gain two documents and a skill and lose nothing; the installer's behaviour is unchanged apart from its output, so no reinstallation is needed and no configuration entry was added or changed. The managed file count goes from 38 to 41 — the setup procedure, this record, and the `foundation-setup` skill. All 41 were assessed for removal and none is safely removable: 32 are referenced by path or filename from a document, template, profile or script, the 9 skills are the entry points Codex discovers from `.agents/skills/` rather than things documents link to, and the `templates/stacks/` files are reached through the directory pointer in engineering standards. Nothing was removed, and no file should be without a reviewed migration, since the installer deletes managed files dropped upstream and an adopter would lose them on the next update. The adoption document becomes the mechanism reference behind setup rather than the entry point, and the README leads with the sentence a human says. The procedure is prose and enforces nothing: an agent can skip a step, and only the committed diff and the handoff show whether it did, which is why the completion test is written as conditions a reviewer can check rather than as a claim the agent makes. To recover, delete the two new files and revert the installer's output block; nothing else depends on them.

Evidence: `python3 scripts/validate.py` and `python3 -m unittest discover -s tests -v` pass, with the skill count raised to nine and 38 tests covering a fresh install, an existing `AGENTS.md` with and without a mention of the configuration, a mention that forbids it, a root `AGENTS.override.md`, nested instructions needing reconciliation, a repeated run, a resumed setup needing no checkout, a partially configured project, and a foundation directory the installer does not own. The starting instruction was exercised end to end and the transcript kept rather than summarised. The pilot's real installation was found to be a skeleton of empty directories with no manifest and no configuration, which the installer correctly refused to adopt; restoring it is recorded with this change. No check can verify that an agent actually follows the procedure, or that a human answered the handoff rather than ignoring it — both are visible only in the resulting diff.
