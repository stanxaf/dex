# ADR 0003: Keep agent operations always-read and defer only the deployment gate

Status / owner / date / approving authority: accepted on 2026-11-07. Owner and approving authority: **Stan**, the foundation owner who approved reducing the always-read instruction set as part of the AGT-12 work. The approval covers the arrangement recorded here. It does not approve dropping any requirement, and none was dropped.

Scope and non-goals: keeps [agent operations](../security/agent-operations.md) as a single always-read document covering the agent's tool surface, session credentials, data access and automated runs, and defers one block — the [deployment gate](../security/deployment-gate.md) — read only before an automated deployment. Removes duplicated text from the workflow, engineering standards and quality gates to pay for the new rules. Updates the reading tiers in `templates/project/ai-governance.md`, the adoption guidance, the baseline and web-saas profiles and the validator. No approval boundary moved.

Context and constraints: INS-5 makes the always-read tier a cost decision and INS-6 requires the always-loaded set to stay within a recorded budget, because Codex drops guidance past its instruction-size limit without saying so. INS-6 also warns that a reference is a weaker control than inclusion, so moving text out of the tier reduces control rather than saving for free. The committed baseline for the always-read foundation set is 2,417 words, and this revision adds eight rules to it: AGT-15 to AGT-21 for the deployment gate and AGT-22 for the instruction bootstrap, plus a mandatory expiry requirement in the workflow.

Options considered: (1) compress the always-read prose in place — rejected for the rule text itself, because the verbose clauses in AGT-1 to AGT-3 carry the operative detail that resists prompt injection and compressing them is weakening disguised as editing; (2) split agent operations into a core and a broad detail tier triggered per action — tried, measured and rejected, because a tool-using session fires the tool, credential and data triggers immediately and so read 3,443 words against the 2,417 it read before, a 42 percent increase for ordinary work in exchange for a 1.8 percent cut in the always-loaded set; (3) defer the quality-gates table behind a trigger — rejected, because it would re-complicate the tier model that option 2 showed to be the wrong shape; (4) keep one always-read document, defer only requirements that almost never apply, and fund the new rules by removing duplication — adopted. Only the deployment gate qualifies for deferral.

Decision and rationale: ordinary work, including ordinary tool-using work, reads one document. AGT-1 to AGT-14 and AGT-22 stay always-read because each is reachable on a normal task: content handling on every request, tool and credential rules the moment a tool is used, data classes the moment a fixture is touched, and incident response at the moment damage occurs, when nobody will stop to follow a reference. Only AGT-15 to AGT-21 are deferred, because an automated deployment is rare, deliberate and announced well in advance, so the trigger fires on a decision rather than on a reflex. Three properties keep the deferral honest: AGT-12 states the prohibition in full in the always-read document, so an agent that never opens the gate is governed by a restrictive default rather than by silence; the trigger states that not having read the gate is never grounds for proceeding; and AGT-22 resolves the bootstrap, since no rule can be followed before the instruction set is loaded. AGT-22 grants the minimum for that purpose — read-only, instruction files only, and where no file-reading tool exists the specific read-only commands needed to read those paths, explicitly not a broader shell session — and reaches no data, network or write.

Three further corrections came from review. Decision expiry is now mandatory in the active instructions rather than a convention of these two records: the workflow requires every decision and exception record to carry an explicit expiry and state what an overdue one changes, and requires an overdue or expired record to be read restrictively, treated as unreconciled and reported. A rule living only in an ADR governs nothing, because ADRs are in no reading tier. AGT-9 keeps the original synthetic-or-de-identified default, which two earlier drafts of this work damaged in opposite directions — one making the default conditional on a project enumerating its data classes, the next withdrawing de-identified data from the default altogether and so requiring class permission for ordinary de-identified test data. Both were authorization changes no finding had asked for. The rule now states the default plainly and adds only what was genuinely missing: an explicit project restriction binds whatever form the data takes, so a de-identified or masked extract of a restricted class and model output built from its real records fall under that restriction rather than escaping it by transformation; obtaining either from production is itself a production data operation needing the approval such an operation requires, which keeps the boundary at reading production rather than at what follows; and an explicit permission for fictional fixtures inside a restricted domain governs. Third, the validator now checks that every decision record carries an expiry and overdue handling, so the new workflow rule is enforced rather than trusted, and [ADR 0001](0001-distribution.md) was brought under it — with its missing owner and approval date recorded as gaps rather than reconstructed, since inventing an approver would turn an acknowledged gap into a false audit record.

Consequences, migration and recovery: measured at acceptance, the always-read foundation set is 2,398 words against the committed baseline of 2,417, a reduction of 19 words, and that is the figure the review asked for — ordinary work now reads less than before while eight rules were added. The movement by document: workflow 875 to 737, engineering standards 371 to 336, quality gates 263 to 223, agent operations 908 to 1,102. The deployment gate holds 843 words that only an automated deployment reads, putting that path at 3,241. Counting the project-owned files a web-saas adopter also loads — root `AGENTS.md`, the configuration and both profiles — the full ordinary cost is 2,928 against a committed 2,942, so the reduction holds when nothing is excluded from the count. The margin is thin on purpose: later correctness fixes — restoring the complete installed profile paths, and settling the data-class rule — were allowed to cost words rather than be traded against the budget, since a budget met by leaving a rule wrong is not met. Every reduction is removal of duplication or of material that does not apply to an adopter, not removal of a requirement: the workflow's quick-reference bullets summarised sections in the same always-loaded file, its roles and evidence sections restated the review template's finding format and the quality-gates pass rule, its "Based on" list and Codex loading mechanics moved to [Codex compatibility](../agent-governance/codex-compatibility.md) where the other external sources already live, engineering standards restated AGT-1 to AGT-3 rather than pointing at them, and quality gates described this repository's own CI to adopters who never run it. The project-owned files went from 525 to 528 words even though the configuration gained two entries — egress destinations and the deployment gate — because the entries themselves were rewritten to record a project's answer rather than re-explain the rule they cite, which is what INS-2 asks of a project file, and the baseline profile stopped summarising the standards it names. Adopters add two entries, rename one label and find most other entry wording changed without a new decision behind it; `.ai-governance.md` is never overwritten by the installer, so their existing answers stand until they choose to edit them. To recover, concatenate the deployment gate back into agent operations and restore the previous tier line; that direction enlarges the always-read set and is therefore the safe one.

Evidence: `python3 scripts/validate.py` and `python3 -m unittest discover -s tests -v` pass, including the reading-tier target check, the rule-uniqueness check, the citation-resolution check that catches a rule reference left dangling by a move or renumber, the decision-record checks that require a parsed `Expiry date` and `Review by` field and handling that addresses the overdue case, and the installer test that an update adding a document leaves `.ai-governance.md` byte-identical. The validator also reports, without failing, any decision record still holding an unfilled owner placeholder. The date fields replaced an earlier check that matched dates in prose by proximity, which let a single review date satisfy a search for an expiry; a test now fixes that case so it cannot return. Word counts are from `wc -w` on the documents named in the template's reading-tier lines; an adopter with larger instruction files should re-measure. No check can verify that an agent actually follows the trigger and reads the deployment gate; that is runtime behavior and must be observed in the agent's environment, per INS-6 and Codex compatibility.

Expiry and review handling: both dates above fail toward more instruction being loaded rather than less. No rule expires with the record, because none was created by it; every deferred requirement stays in force whether or not the review happens. Re-measure the always-loaded set and the per-session cost at review, since both drift as documents change, and recombine if ordinary work has come to read the deployment gate anyway. The workflow governs the overdue case uniformly — an overdue record falls back to the requirement it modified — and what this record modified is the reading tier of the deployment gate. So from **2027-05-07** without a completed review the deferral ends and the deployment gate returns to the always-read tier, and the lapse is also reported as unreconciled instruction hygiene under INS-7, counting against the reconciliation date that rule requires. An earlier draft of this record let the deferral stand past the review date on the reasoning that the trigger still held; that was a quieter outcome than the workflow allows, and it is removed, because a tier arrangement nobody has re-examined is exactly what the fallback rule exists to undo. Expiry on **2028-11-07** has the same immediate effect and differs in what restores the deferral: the owner must re-approve the arrangement by superseding this record. That is a safe landing because it enlarges the loaded set, costing attention rather than protection, which is the opposite direction from the usual expiry risk. Two conditions bring review forward without waiting for either date: evidence that the trigger is being skipped returns AGT-15 to AGT-21 to the always-read tier immediately, and a new requirement landing in the deferred tier reopens whether the trigger still covers it.
