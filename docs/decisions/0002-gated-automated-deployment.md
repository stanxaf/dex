# ADR 0002: Gated automated deployment under AGT-12

Status / owner / date / approving authority: accepted on 2026-11-07. Owner and approving authority: **Stan**, the foundation owner who holds the decision AGT-12 recorded as theirs. The approval is a policy approval: it permits the gated pattern below and approves no deployment, pipeline, environment or release, is not evidence that any existing automation conforms, and does not stand in for the release-specific approval AGT-15 requires.

Scope and non-goals: resolves the open question attached to AGT-12 in [agent operations](../security/agent-operations.md) and adds AGT-15 to AGT-21 in the [deployment gate](../security/deployment-gate.md). Other approval boundaries are unchanged, in the workflow and in the web-saas and regulated profiles. No infrastructure, pipeline or permission is created or altered by this record; the foundation states policy and configures nothing.

Context and constraints: AGT-12 prohibited any non-interactive run from holding production credentials or writing to protected branches, environments or data. Written as a flat prohibition it also banned an approved, gated deployment pipeline, which holds production credentials by design and is a legitimate and common pattern. The document carried that conflict as an explicit unresolved note rather than a carve-out, so projects deploying through CI had no conforming path. The prohibition could not simply be relaxed: the risk it addresses is that automation removes the human from an approval boundary, and most of that risk survives any rewording. Whatever replaced it had to reconstruct the human decision somewhere the agent cannot reach.

Options considered: (1) leave AGT-12 as written — keeps the rule simple, but makes the foundation unusable for projects that deploy through CI and pushes them into undocumented local exceptions, which is worse than a stated rule; (2) permit automated deployment under a standing or blanket approval — rejected, because a standing approval approves no particular artifact and is the specific failure the prohibition exists to prevent; (3) remove production deployment from the agent approval boundaries — rejected as weakening a security control, and it needs an approval nobody sought; (4) bind the approval to a release or version string and check it once at approval time — rejected on review, because a tag, build number or `latest` can be repointed or rebuilt after approval, so the approval and the deployed bytes diverge without anyone overriding anything; (5) bind to a digest and verify at the gate, but let the deploying step resolve its own reference — rejected on further review, because verification and execution then read different things and the reference can move in the interval; (6) bind and verify the artifact digest alone — rejected on further review again, because the same artifact deployed with different configuration is a different deployment: manifests, values, secret references, the migration set and flag state all change what runs, and a gate blind to them approves one thing and ships another; (7) bind, verify and execute against a complete release identity — artifact digest, pinned configuration revision and target environment identifier — adopted.

Decision and rationale: AGT-12 keeps its default and names one exception, conditioned on every requirement in the deployment gate. The gate's organising idea is release identity: the complete deployable unit, immutably identified by the artifact's content digest, the deployment configuration pinned by digest or immutable revision, and the target environment's stable identifier, where changing any one produces a different release needing its own approval. AGT-15 binds the approval to that identity, so an approval that pins the artifact while leaving configuration floating has approved nothing checkable. AGT-16 has the gate resolve all three components it would actually act on, compare them against the approved release, and refuse on mismatch or on a component it cannot resolve, with a matching artifact under changed configuration counted as a mismatch rather than a detail. AGT-17 closes the remaining window by requiring the deployment to act on those exact three identities as given, since re-resolving a tag, a config branch or an environment alias after verification makes the comparison prove nothing about what ran. AGT-18 keeps the gate, the verification and the configuration a release pins outside the agent's reach. AGT-19 requires least-privilege, run-scoped, expiring credentials. AGT-20 requires evidence carrying all three components of both the approved and the deployed release plus the comparison result. AGT-21 preserves the workflow and profile approvals in full. Failing any one requirement leaves the prohibition in force, so the exception cannot be reached by partial compliance.

Consequences, migration and recovery: projects that permit automated deployment record the gate, the approver, what a release identity pins, how the gate compares all three components, how the deploying step applies them as given, credential scope and lifetime, and the evidence location, in `.ai-governance.md` under the AGT-15 to AGT-21 entry; until that entry is completed the configuration is unreconciled and AGT-12's default applies. Three concrete migration costs: a pipeline identifying artifacts only by tag needs a digest, a pipeline tracking configuration on a branch needs it pinned to a revision, and a deploying step that cannot accept identities for all three components needs changing. Existing pipelines are not grandfathered — one that cannot show a conforming gate was already prohibited and remains so. The rules are prose and enforce nothing: the gate, the release comparison, credential scopes and audit log live in the platform and must be verified there. To recover, revert this record with the AGT-12 change and the deployment gate together; because the default was kept intact, reverting restores the previous prohibition without leaving a gap. This is a change to a foundation requirement by its owner, so it is recorded here rather than as an exception under INS-8, which covers a project loosening a foundation rule.

Evidence: `python3 scripts/validate.py` and `python3 -m unittest discover -s tests -v` pass on this change; both check structure and the installer, and neither can verify that any pipeline meets AGT-15 to AGT-21 — that is a per-project review. Reviewed scenarios are recorded with this change: an approved release deployed unchanged to the approved environment passes; the same tag rebuilt to different bytes after approval fails AGT-16 and is refused rather than redeployed; a tag re-resolved by the deploying step after a passing check fails AGT-17 even though the gate's comparison succeeded; **a changed configuration against an unchanged, approved artifact fails AGT-15 and AGT-16, because the release identity differs even though the digest matches**; an approval for staging used to reach production fails AGT-15 and AGT-16; and evidence naming a release without its component identities fails AGT-20.

Expiry and review handling: both dates above are required of every decision record by the workflow rather than left to the author. The protections never lapse: AGT-12's prohibition and AGT-15 to AGT-21 as conditions are standing requirements, and neither date deletes, suspends or softens one. What lapses is this record's standing to permit, and the workflow governs that uniformly — an overdue or expired record falls back to the requirement it modified. Here that requirement is AGT-12, so from **2027-05-07** without a completed review the automated path is suspended: a non-interactive run may not hold the production credentials this record would otherwise allow, and a release instead goes through the workflow's ordinary production-deployment approval with the human in the session. Deployment is not blocked; the automation is, and the lapse is reported in any review or deployment evidence that touches it. An earlier draft let a pipeline already relying on the exception continue unchanged past the review date. That contradicted the workflow rule, which forbids relying on a lapsed record, so it is removed: because the interactive fallback keeps releases shipping, the carve-out protected nothing and only invited drift. At expiry on **2028-11-07** the automated path additionally cannot return until the owner re-approves by superseding this record, and a new pipeline, environment or materially changed one may not use the exception from that date. Expiry therefore fails toward restriction while leaving a working route to production. Bring either date forward on the first report of a conforming gate that is still unsafe, or of a legitimate deployment these requirements wrongly exclude.
