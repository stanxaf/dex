# ADR 0005: Verification at task checkpoints

Status / owner / date / approving authority: proposed on 2026-11-08 at the user's request. Owner and approving authority: **[OWNER NAME PENDING]** — the foundation owner; their name has not been verified. Fill before merge.

Scope and non-goals: define a feedback checkpoint for exploration and select verification for the outcome, risk and destination. Preserve project and profile requirements, security and approval boundaries, required checks, separate review before merge, and release verification. Do not change installer behavior or automatically alter consuming projects.

Context: designers and developers often explore an idea through multiple small changes before deciding whether to ship it. The existing workflow requires a verified batch, proportionate checks and tests for changed behavior, but does not distinguish feedback on an idea from a completed change. Agents may consequently repeat release-oriented checks during exploration or report an exploratory result ambiguously. The existing rules did not require every check after every edit, so no particular previous time saving can be claimed.

Decision and rationale: the workflow defines exploration, wrap-up, commit or push, and completion or release checkpoints. An exploratory result may be ready for feedback with later checks explicitly deferred; it is not a verified completed change. The destination and actual rules determine what applies to a commit or push. Results may be reused only while relevant inputs remain unchanged. Project and profile requirements can require earlier checks; no checkpoint permits bypassing a required check, approval or protected environment. The engineering and testing guidance and implementation skills refer to the checkpoint timing, while the workflow remains the canonical rule. Review skills distinguish inspecting evidence from rerunning checks and retain independent review before merge.

Alternatives: requiring release verification for every exploration costs time before an idea is selected. A universal prototype mode that waives tests or treats every non-production branch as safe would hide risks and conflict with project rules. A separate workflow per persona or agent duplicates the policy and can drift. Checkpoints leave the team free to choose useful early checks while making the final obligations explicit.

Consequences, migration and recovery: a project receives the change only after a reviewed foundation update. Its configuration and instructions are not overwritten; stricter local rules continue to apply and need separate review if the owner wants to revise them. The task template gains checkpoint and deferred-check prompts; existing project-owned configurations gain no required entry. Revert the changed foundation documents and skill instructions to recover the previous verification timing. The installer and all existing checks remain in place.

Evidence: before this change, `python3 scripts/validate.py` passed with the existing ADR 0004 owner placeholder reported; `python3 -m unittest discover -s tests -v` passed 77 tests with four skips under the available Python interpreter. The changed guidance was reviewed against exploratory UI, a stricter local documentation rule, a work-in-progress checkpoint and release preparation; the worked example records those cases. The baseline always-read foundation documents increased from 2,706 to 2,997 words, measured with Python whitespace splitting. These checks and examples do not measure agent adherence, token use or time saved; record actual outcomes in the implementation report.
