# Adoption and updates

The Python installer uses only the standard library and copies a locally reviewed source checkout; it does not fetch code or require a central service. It manages only the docs, profiles and named skills recorded in `.ai-foundation/manifest.json`. It creates a project config and root `AGENTS.md` only when absent; these are project-owned and never automatically updated. Existing root or nested instruction files are listed for **manual semantic review**, not interpreted. Check global instructions, `AGENTS.override.md`, nested instructions, fallback names, design system and project policies for contradictions. Resolve or document an approved exception before activation. Do not assume rules referenced in a file are automatically included in Codex's native instruction chain.

Run `python3 scripts/install.py /path/to/project --profile web-saas` from a reviewed checkout. `--profile` is used only when creating `.ai-governance.md`; change the existing config manually to switch profiles. When an explicit selection conflicts with the recognizable existing profile, the installer reports it without changing the config. The content digest identifies exact managed content; the Git revision is informational and may have uncommitted changes. Commit the installer output along with the reviewed config in the consuming project. Do not edit managed files; put extensions and exceptions in project-owned files.

For an update, review source changes and run the installer again. It checks every old managed file for modification or absence, rejects occupied new paths and symlinked managed paths, then replaces only previously recorded files. It refuses unknown or malformed manifests. It does not remove unmanaged material or modify project instructions. A file-by-file update is not transactional: if interrupted, stop and restore the affected managed files and manifest from the consuming project's last commit (preserving unrelated work), then retry. Back up uncommitted work before updating. Hashes detect changes, not hostile tampering; trust and review the source. The installer cannot determine whether instructions are mutually compatible.

An update can add managed documents, change which documents your configuration must point to, and introduce entries the foundation now requires. The installer delivers the documents and still does not touch `.ai-governance.md`, because that file is project-owned; nothing is overwritten and nothing is filled in for you. Because the installer output is committed, compare the managed template against its own previous version rather than against your configuration, which holds project values the template never will: after updating, run `git diff HEAD -- .ai-foundation/templates/project/ai-governance.md`. Compare against `HEAD` rather than the index, so the comparison holds whether or not the installer output has already been staged; omitting `HEAD` reports nothing once it is staged. Apply both kinds of change it reports. An **added** line is an entry to copy into your configuration and complete with actual project values. A **changed** line is an entry you already hold whose required content moved, most often the `All work` and `When relevant` document lists; your copy keeps the old text until you edit it, so reconcile those lines instead of assuming additions are the only thing to apply.

This revision contains both kinds. The `All work` list gains agent operations and the `When relevant` list gains instruction hygiene, and five entries are added: the permitted tool and MCP server inventory (AGT-4), the expected approval mode and sandbox posture (AGT-6), the data classes an agent session may read (AGT-9), whether non-interactive runs are permitted (AGT-12), and the instruction reading tiers, budget and last reconciliation (INS-5 to INS-7). The baseline profile now also names agent operations and instruction hygiene. A document absent from your `All work` line is not read on routine work, so a stale reading tier drops a requirement silently rather than failing visibly. Until an added or changed entry is applied it is unreconciled configuration, not a statement that the requirement does not apply, and the work it governs should be treated as such. Review the installed documents before completing the entries, since each one records a decision those documents require you to make.

Codex sandbox policy may protect existing `.agents` directories: run installation from an appropriately authorized terminal or grant the necessary permission. No permission settings are changed by this foundation.
