# Adoption and updates

The Python installer uses only the standard library and copies a locally reviewed source checkout; it does not fetch code or require a central service. It manages only the docs, profiles and named skills recorded in `.ai-foundation/manifest.json`. It creates a project config and root `AGENTS.md` only when absent; these are project-owned and never automatically updated. Existing root or nested instruction files are listed for **manual semantic review**, not interpreted. Check global instructions, `AGENTS.override.md`, nested instructions, fallback names, design system and project policies for contradictions. Resolve or document an approved exception before activation. Do not assume rules referenced in a file are automatically included in Codex's native instruction chain.

Run `python3 scripts/install.py /path/to/project --profile web-saas` from a reviewed checkout. `--profile` is used only when creating `.ai-governance.md`; change the existing config manually to switch profiles. When an explicit selection conflicts with the recognizable existing profile, the installer reports it without changing the config. The content digest identifies exact managed content; the Git revision is informational and may have uncommitted changes. Commit the installer output along with the reviewed config in the consuming project. Do not edit managed files; put extensions and exceptions in project-owned files.

For an update, review source changes and run the installer again. It checks every old managed file for modification or absence, rejects occupied new paths and symlinked managed paths, then replaces only previously recorded files. It refuses unknown or malformed manifests. It does not remove unmanaged material or modify project instructions. A file-by-file update is not transactional: if interrupted, stop and restore the affected managed files and manifest from the consuming project's last commit (preserving unrelated work), then retry. Back up uncommitted work before updating. Hashes detect changes, not hostile tampering; trust and review the source. The installer cannot determine whether instructions are mutually compatible.

An update can add managed documents, change which documents your configuration must point to, and introduce entries the foundation now requires. The installer delivers the documents and still does not touch `.ai-governance.md`, because that file is project-owned; nothing is overwritten and nothing is filled in for you. Because the installer output is committed, compare the managed template against its own previous version rather than against your configuration, which holds project values the template never will: after updating, run `git diff HEAD -- .ai-foundation/templates/project/ai-governance.md`. Compare against `HEAD` rather than the index, so the comparison holds whether or not the installer output has already been staged; omitting `HEAD` reports nothing once it is staged. Apply both kinds of change it reports. An **added** line is an entry to copy into your configuration and complete with actual project values. A **changed** line is an entry you already hold whose required content moved, most often the `All work` and `When relevant` document lists; your copy keeps the old text until you edit it, so reconcile those lines instead of assuming additions are the only thing to apply.

This revision contains both kinds. `docs/security/deployment-gate.md` is a new managed document holding the conditions an automated deployment must meet, so the `When relevant` list gains it; it is read only before an automated deployment, and ordinary work does not reach it. Agent operations keeps its path and its place on the `All work` line, and it remains the single document covering tool surface, session credentials, data access and automated runs, so tool-using work needs no second document. `AGT-4`, `AGT-6`, `AGT-9` and `AGT-12` in your configuration still cite live rules in the same document as before.

Two entries are genuinely new and need an answer from you: the permitted network egress destinations (AGT-7) and the automated deployment gate (AGT-15 to AGT-21). One label was renamed, from `Reading tiers, instruction budget and last reconciliation` to `Reading tiers and reconciliation`, with the same content behind it. Most other entry lines also changed wording, because each was rewritten to ask for the project's answer instead of re-explaining the rule it cites — those carry no new decision, so an answer you already wrote remains valid and needs copying across only if you want the shorter prompt. The `When relevant` line and the data classes entry (AGT-9) are the two whose meaning moved; read the next paragraph before reconciling them.

Four changes alter meaning rather than only wording, so re-read them even where your existing text still looks valid. **AGT-12:** a non-interactive run is still restricted by default, but an automated deployment through a conforming gate is now permitted. The gate binds approval to a complete *release identity* — the artifact's content digest, the deployment configuration pinned by digest or immutable revision, and the target environment's stable identifier — then verifies all three before releasing credentials and applies exactly those, never re-resolving a tag, config branch or environment alias. The same artifact with changed configuration is a different release needing its own approval, so a pipeline that pins the image but tracks configuration on a branch does not conform, nor does one whose deploying step cannot accept identities for all three. **AGT-9:** synthetic or de-identified data remains the default and needs no entry, so routine fixtures and de-identified test data are unaffected. Two things are now explicit rather than new. An explicit project restriction binds whatever form the data takes, so a de-identified or masked extract of a restricted class, and model output built from its real records, fall under that restriction instead of escaping it by transformation. And obtaining either from production is itself a production data operation, so de-identifying production data needs the same approval as copying it — the approval boundary sits at reading production, not at what you do with it afterwards. Name the readable real-data classes and any restricted class, and if your project permits fictional fixtures inside a restricted domain, record that permission and it governs. **AGT-7:** a recorded egress policy bounds every fetch, including one the task plainly requires, so a destination outside it is an addition to approve; where no policy is recorded, necessity governs as before and what was fetched is reported. **Decision expiry:** the workflow now requires every decision and exception record to carry an explicit expiry and state what an overdue one changes, and an overdue or expired record never widens permission — read it restrictively, treat what it authorized as unreconciled, and report the lapse. Record the expiry and review date of each of your own records in the entry for them.

Leaving the deployment entry unset means not permitted. AGT-22 needs no entry: it permits reading the instruction set itself, read-only — including, where the environment has no file-reading tool, the narrow read-only commands needed to read those paths — and reaches no data, network or write. The baseline and web-saas profiles now point automated deployment at the deployment gate, and the baseline profile no longer summarises the standards it names, since restating them was the contradiction INS-2 warns about. Reading cost fell despite the additions: the always-read foundation set is 33 words smaller than the revision you are upgrading from, and 36 smaller counting your own `AGENTS.md`, configuration and profiles. Duplicated text was removed from the workflow, engineering standards and quality gates, every requirement it duplicated is still loaded elsewhere, and the external-source list the workflow carried now sits in [Codex compatibility](codex-compatibility.md).

See [ADR 0002](../decisions/0002-gated-automated-deployment.md) for the deployment decision and [ADR 0003](../decisions/0003-instruction-reading-tiers.md) for the reading tiers and their measured cost; both are owned and approved by Stan, and both carry an explicit expiry whose overdue handling narrows what is permitted rather than dropping a protection. [ADR 0001](../decisions/0001-distribution.md) was brought under the same expiry rule; it records no owner or approval date and neither was reconstructed, so treat its owner as unrecorded. Your own records need the same treatment: the workflow now requires every decision and exception record to carry an expiry and say what an overdue one changes, so audit the records you already hold rather than assuming the rule applies only to new ones. If one is already overdue, fall back to the requirement it modified and report it — an overdue record cannot be the authority for continuing.

If you are adopting from a revision earlier than the previous one, that revision's changes still apply and are not repeated by this one: the `All work` list gained agent operations, the `When relevant` list gained instruction hygiene, the baseline profile gained both, and four entries were added — the permitted tool and MCP server inventory (AGT-4), the expected approval mode and sandbox posture (AGT-6), the data classes an agent session may read (AGT-9), and the instruction reading tiers, budget and last reconciliation (INS-5 to INS-7). Apply them alongside this revision's.

A document absent from your `All work` line is not read on routine work, and one absent from `When relevant` is not read even when its trigger fires, so a stale reading tier drops a requirement silently rather than failing visibly. Until an added or changed entry is applied it is unreconciled configuration, not a statement that the requirement does not apply, and the work it governs should be treated as such. Reconciling the tiers is an edit to your own configuration; the installer never writes that file, so nothing here is overwritten and nothing is applied for you. Review the installed documents before completing the entries, since each one records a decision those documents require you to make.

Codex sandbox policy may protect existing `.agents` directories: run installation from an appropriately authorized terminal or grant the necessary permission. No permission settings are changed by this foundation.
